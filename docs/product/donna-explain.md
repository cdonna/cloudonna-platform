# Donna Explain

**Status:** Product design principles for explainability. No code changes
in this document — but unlike some of the other documents in this set,
most of the machinery this describes **already exists** (Sprint 3's
scoring engine, Sprint 5.1's intelligence layer). This document is as much
a naming and completeness exercise as a design one.

## The rule

Every recommendation Donna produces must be able to answer eight
questions, unprompted, without the user needing to ask. If any one of
these eight can't be answered for a given recommendation, the
recommendation is not ready to show — see `donna-trust-framework.md`,
"Confidence Model," for what happens instead.

## The eight questions

### 1. Why?

*What made this the top-ranked option.*

**Already built:** `DecisionOutput.recommendation.dimensions[].positiveEvidence`
(Sprint 3, per-dimension evidence strings) and
`IntelligenceEnrichment.recommendationNarrative` (Sprint 5.1, prose
version of the same facts). The deterministic layer produces the *what*;
the narrative layer produces the *why, in words a board reads*. Both
trace to the same underlying scores — the narrative is never a second,
independent opinion.

### 2. Why not (the alternatives)?

*What made the other shortlisted options score lower — not just "there
were alternatives," but specifically why they lost.*

**Already built:** `DecisionOutput.alternativeRecommendation`,
`.alternatives[]`, and `IntelligenceEnrichment.alternativeNarrative` +
`.keyTradeOffs[]`. The trade-off narrative is generated by directly
comparing dimension scores between the primary and the alternative
(`buildKeyTradeOffs` in `deterministic-provider.ts`) — every trade-off
sentence names a real score gap, never a general impression.

### 3. Evidence

*What specific, sourced facts support the recommendation.*

**Already built:** `positiveEvidence`/`concerns` (`EvidenceItem[]`,
Sprint 3) at the deterministic layer, and `sourceReferences` +
`EvidenceReliability` tiers (Sprint 5.1's `EvidencePackage`) at the
retrieval layer. The reliability tiering
(`primary_source`/`vendor_published`/`analyst_report`/`internal_review`)
exists specifically so evidence is never presented as uniformly
authoritative — a vendor's own claim about itself and an independent
analyst's finding must never look the same in the UI once this is wired
into a result screen.

### 4. Trade-offs

*What you gain and give up by choosing this option over the alternative.*

**Already built:** `IntelligenceEnrichment.keyTradeOffs[]`. Distinct from
"Why not" (question 2) in framing: "why not" explains the alternative's
weakness; "trade-offs" explains the primary's own cost. Both are needed —
a recommendation that only explains why it won and never what it costs is
a sales pitch, not an explanation.

### 5. Risks

*What could go wrong with this choice, specifically.*

**Already built:** `DecisionOutput.risks[]` (deterministic, template-derived
from constraints — e.g. tight budget, aggressive timeline, vendor
concentration) and `IntelligenceEnrichment.risksNarrative` (prose framing
of the same list). Risks are never invented by the narrative layer — see
`donna-trust-framework.md`, "Evidence-First": the narrative can only frame
risks the deterministic layer already identified.

### 6. Alternatives

*What else was considered and shortlisted, not just the runner-up.*

**Already built:** the full `alternatives[]` array (up to the shortlist
size — three platforms today, `MAX_SHORTLIST_SIZE` in
`knowledge-provider.ts`) plus the Comparison Matrix (Sprint 3) for a
side-by-side view across all shortlisted platforms.

### 7. Missing information

*What Donna does not know that would have changed or sharpened this
recommendation.*

**Already built:** `EvidencePackage.knownInformationGaps[]` and
`IntelligenceEnrichment.missingInformation[]` (Sprint 5.1) — computed from
real signal gaps (a dimension with zero positive evidence, an overall low
confidence score), never a generic disclaimer. This is the question most
comparison tools skip entirely, because admitting a gap looks like
weakness. Treated here as a first-class, always-answered question — see
`company-constitution.md`, "Intellectual Honesty."

### 8. Confidence explanation

*Not just a confidence number — why that number, specifically.*

**Already built:** `computeConfidence()` (Sprint 2, input completeness +
signal quality) produces the number; `IntelligenceEnrichment.confidenceExplanation`
(Sprint 5.1) explains it in one sentence tied to the actual gaps found
(`buildConfidenceExplanation` in `deterministic-provider.ts`). A
confidence score with no explanation is a number pretending to be an
argument — Donna never shows one without the other.

## What "answer" means, precisely

For each of the eight, "answered" means: **a specific string exists,
traceable to a specific computed fact, rendered next to the
recommendation** — not "answerable if asked," not "available in a
tooltip," not "true in principle but not currently displayed." The gap
today is not in the data model (seven of eight questions already have a
populated field, as shown above) — it's that none of this is wired into
`ResultPanel` yet. Wiring `IntelligenceEnrichment` into the result UI
(Sprint 5.1 Phase 1's proposed Phase 5.5) is what turns "the data exists"
into "the recommendation actually explains itself."

## The one failure mode to design against

A recommendation that answers all eight questions fluently but
*inconsistently* — where the prose narrative and the underlying evidence
quietly diverge — is more dangerous than one that answers none of them,
because it looks trustworthy. This is exactly why `evidenceReferences`
validation and the unsupported-numeric-claim check
(`findUnsupportedNumericClaims`, Sprint 5.1) exist: not as generic input
hygiene, but as the direct mechanical enforcement of this document's
entire premise. Explainability without a way to verify the explanation
against the facts is just better-written marketing copy.
